# مهارة التدقيق الصارم لمنع البيانات الوهمية (Zero Fake Data Auditor)

## 1. طبيعة عمل المهارة
* **نمط التشغيل:** **تلقائي ودائم (Autonomous / Background)** — تعمل تلقائياً كجزء من وعي المهندس التنفيذي أثناء كتابة أو فحص أي كود دون حاجة لتذكير مدير المشروع.
* **النطاق:** شامل لكافة المشاريع البرمجية المؤسسية (Frontend, Backend, APIs, Database).

---

## 2. المحظورات الصارمة (Strict Prohibitions)
1. **حظر مصفوفات البيانات الوهمية (No Mock Arrays):** يُحظر كتابة مصفوفات ثابتة في الواجهات لتمثيل المستخدمين أو التذاكر أو المعاملات مثل `const mockTickets = [...]` أو `const dummyStats = {...}`.
2. **حظر التوكنات الالتفافية (No Dummy Auth):** يُمنع وضع أي توكنات مصادقة وهمية (مثل `mock-admin-token-123`) أو تجاوز فحص الـ JWT في بيئة التطوير.
3. **حظر قياسات الأداء المفبركة (No Fake Telemetry):** يُمنع كتابة نسب مئوية أو أزمنة استجابة عشوائية (`Math.random()`) في لوحات المراقبة ولوحات التحكم.
4. **حظر البوابات الخلفية (No URL Bypass):** يُمنع استخدام بارامترات في الرابط مثل `?login_as=admin` لتخطي شاشة تسجيل الدخول.

---

## 3. البروتوكول الإلزامي للبدائل الحقيقية
* عند الحاجة لبيانات في الواجهة: كتابة استعلام API حقيقي مربوط بـ Express / Prisma / PostgreSQL.
* عند الحاجة لمصادقة: الاعتماد على مسار تسجيل الدخول الرسمي المشفر بـ `Argon2id` و `HttpOnly Cookie`.
* عند الحاجة لمقاييس الخادم: جلب بيانات العتاد الفعلي عبر مكتبات النظام الحقيقية (مثل `os.cpus()`, `os.freemem()`, Prisma counts).

---

## 4. قائمة التحقق الآلي قبل الاعتماد (Checklist)
- [ ] التأكد من عدم وجود متغير يبدأ بـ `mock`, `dummy`, `fake`, `stub` في ملفات الإنتاج.
- [ ] التأكد من أن كل جدول أو قائمة تسحب بياناتها عبر `useQuery` أو `fetch` من مسار API حقيقي.
- [ ] التأكد من وجود حالات حقيقية للتحميل (Loading Skeleton) والخطأ (Error State) والفراغ (Empty State).
