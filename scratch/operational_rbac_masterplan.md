# الخطة المعمارية المحدثة: الإدارة اللامركزية للمسارات التشغيلية (Decentralized Flow RBAC)

بناءً على فكرتك الرائعة، سننتقل من نموذج "المركزية المطلقة (الآدمن يتحكم في كل زر)" إلى نموذج **"اللامركزية الموجهة (التفويض للمدراء الميدانيين)"**. 

هذه الفكرة هي بالضبط ما يجعل أنظمة الـ Enterprise ناجحة؛ لأن الآدمن لا يمكنه معرفة قدرات كل موظف فني، بل "رئيس القسم / قائد المسار" هو من يعرف من يستحق أي صلاحية.

## 1. الهيكلة وتوزيع الأدوار الجديد:

### أ) دور الآدمن (مدير النظام - Central Admin):
الآدمن هو صانع المسارات وموزع القيادات.
- يقوم بإنشاء "مسار طلب دعم فني".
- يوجه المسار إلى الإدارة التشغيلية المعنية (مثل: قسم الدعم الفني).
- **يعين "قائد المسار" (Flow Manager)** (مثلاً: مجدي الزروق).
- *بمجرد تعيين القائد، ينتهي دور الآدمن في التفاصيل المجهرية لهذا المسار.*
- إضافة: يمتلك الآدمن صلاحية استثنائية (Override) لإضافة شخص من إدارة أخرى (كالمراجعين أو المدراء التنفيذيين) كـ "مراقب" للمسار.

### ب) دور قائد المسار (مجدي - Flow Manager):
بصفتك القائد، عندما تدخل إلى واجهتك التشغيلية (`/ops`)، سيظهر لك تبويب جديد حصري للقيادات يسمى: **"إدارة الفريق والمسارات (Team Management)"**.
- في هذه الشاشة، ستجد قائمة بكل الموظفين المدرجين تحت إدارتك.
- عند اختيار موظف، ستظهر لك "خصائص المسار" المتعلقة به.
- **مفاتيح التحكم (Toggles) المتاحة لك لتعيينها لكل موظف:**
  1. `رؤية الطابور العام` (هل يمكنه رؤية التذاكر الجديدة قبل إسنادها؟ أم يرى فقط ما تحيله أنت إليه؟)
  2. `سحب تذكرة (Pull)` (هل يمكنه تعيين تذكرة لنفسه؟)
  3. `تحويل لزميل (Internal Transfer)` (هل يمكنه تمرير التذكرة لزميل آخر في نفس القسم؟)
  4. `تحويل خارجي (External Transfer)` (هل هو مخول بتمرير التذكرة لقسم آخر إذا اكتشف أنها ليست من اختصاص قسمكم؟)
  5. `إغلاق التذكرة` (أم يجب أن يرفعها لك لتغلقها أنت بعد المراجعة؟)

## 2. الهيكلة في قاعدة البيانات (Prisma DB)
لتنفيذ هذا، سنحتاج لجدول جديد مرن جداً يربط (المستخدم) بـ (المسار):

```prisma
model FlowUserPermission {
  id             String         @id @default(cuid())
  userId         Int            // الموظف
  flowId         String         // المسار (مثال: مسار الدعم الفني)
  
  // الصلاحيات التي يتحكم بها مجدي (قائد المسار)
  canViewPool        Boolean @default(false)
  canPull            Boolean @default(false)
  canTransferInternal Boolean @default(false)
  canTransferExternal Boolean @default(false)
  canResolve         Boolean @default(false)

  // التتبع
  grantedById    Int?           // القائد الذي منحه الصلاحية
  createdAt      DateTime @default(now())
  updatedAt      DateTime @updatedAt

  @@unique([userId, flowId])
}
```

بالإضافة لتعديل في جدول `FlowDefinition` ليحتوي على:
- `managerId`: لتعريف من هو القائد المباشر لهذا المسار (الذي يملك شاشة التوزيع).

## 3. خطة التنفيذ المرحلية (Execution Steps)
إذا اعتمدنا هذه الخطة:
1. **تحديث قاعدة البيانات:** سأقوم بإضافة جدول `FlowUserPermission` وتحديث `FlowDefinition`.
2. **برمجة الـ API:** إنشاء نقاط استدعاء (Endpoints) تسمح لقائد المسار بتغيير هذه المفاتيح لزملائه.
3. **تطبيق القيود في Backend:** تعديل `OperationalQueueController` الذي فحصناه مسبقاً، ليقرأ من هذا الجدول مباشرة. إذا كان `canViewPool = true`، يرى الفني الطلبات المفتوحة. وإلا، لا يرى إلا ما تسنده أنت إليه.
4. **بناء واجهة "إدارة الفريق":** سأقوم ببناء شاشة أنيقة داخل الـ `WorkModeShell` لا تظهر إلا لمن تم تعيينه كـ `managerId` على مسار معين.

هذا التصور يجعل النظام **(موجّهاً ذاتياً - Self-Governing)** ويخفف العبء عن الآدمن، ويضع القوة التشغيلية في يدك كمدير للإدارة الميدانية. 
هل هذا يعكس رؤيتك بدقة لنبدأ فوراً في التنفيذ (بدءاً من قاعدة البيانات)؟
